Rime with your keystrokes.

> **Fork.** This is `librime-stl`, a dependency-trimmed fork of
> [rime/librime](https://github.com/rime/librime): the engine configures and builds
> without Boost, without a host Python and without a host-built `opencc_dict`.
> Everything below is upstream's README, kept verbatim; a `Fork.` quote block and
> the two sections after “Build and install on Linux” are the only additions, and
> [Differences from upstream](#differences-from-upstream) is the full list.

Features
===
  - A modular, extensible input method engine in cross-platform C++ code,
    built on top of open-source technologies
  - Covering features found in a large variety of Chinese input methods,
    either shape-based or phonetic-based
  - Built with native support for Traditional Chinese, conversion to Simplified
    Chinese and other regional standards via OpenCC
  - Rime input schema, a DSL in YAML syntax for fast trying out innovative ideas
    of input method design
  - Spelling Algebra, a mechanism to create variant spelling, especially useful
    for Chinese dialects
  - Support for chord-typing with a generic Qwerty keyboard

Build dependencies
---
  - compiler with C++17 support
  - cmake>=3.12
  - libglog>=0.7 (optional)
  - libleveldb
  - libmarisa
  - libopencc>=1.0.2
  - libyaml-cpp>=0.5
  - libgtest (optional)

Runtime dependencies
---
  - libglog (optional)
  - libleveldb
  - libmarisa
  - libopencc
  - libyaml-cpp

> **Fork.** No Boost is required. These two lists are the only place this fork
> deletes upstream lines: `libboost>=1.74` above and `libboost` in the runtime
> list. Patterns compile with `std::regex`, and schema-supplied patterns go through
> a shared PCRE→ECMAScript translation so schemas written for upstream keep
> working. OpenCC is vendored under `deps/opencc` with its generated tables
> committed under `dict/opencc/`, so neither a host Python nor a host-executed
> `opencc_dict` is needed to build the engine.

Build and install on Linux
---
```
make
sudo make install
```

> **Fork.** Three build graphs exist in this repository and they must not be
> confused. Each has its own build tree, its own dependency source, and its own
> answer to "may it use a system library":
>
> | Graph | What it produces | Build tree | Dependency source | System libs |
> |---|---|---|---|---|
> | A: host engine | `librime.so`/`.a`, `rime_test` | `build/` | distro packages (Linux/Docker/MinGW) or `make deps` | allowed |
> | B: Android cross | `librime.so` for the JNI consumer | `build/android-<abi>/` | `deps/*` cross-built static into a private prefix | refused |
> | C: dictionary toolchain | `dict/opencc/*.ocd2`, `essay.txt` | `dict/tools/.build/` | `deps/opencc`, host build with `OPENCC_BUILD_DATA=ON` | host by design |
>
> Graph C is never installed, so it cannot appear on A's or B's search path; the
> only thing it hands to the engine is committed data under `dict/`.
>
> A's system opencc is not necessarily the vendored one — Debian's
> `libopencc-dev` is 1.1.3 while `dict/opencc/` was generated by the pinned
> 1.1.9 — and the soname (`libopencc.so.1.1`) does not distinguish them. To make
> "which copy did this build actually link" a configured fact instead of a guess,
> `cmake/RimeDepProvenance.cmake` prints every dependency's resolved
> include/library paths (and opencc's detected version versus the pin) at
> configure time. Declaring a prefix upgrades that report to a gate:
>
> ```
> make deps prefix="$HOME/rime-deps"
> cmake -S . -B build -DRIME_DEPS_PREFIX="$HOME/rime-deps" \
>   -DCMAKE_PREFIX_PATH="$HOME/rime-deps" -DCMAKE_FIND_ROOT_PATH="$HOME/rime-deps" \
>   -DCMAKE_FIND_ROOT_PATH_MODE_LIBRARY=ONLY -DCMAKE_FIND_ROOT_PATH_MODE_INCLUDE=ONLY \
>   -DCMAKE_FIND_ROOT_PATH_MODE_PACKAGE=ONLY
> ```
>
> `RIME_DEPS_PREFIX` means: fail the configure if any dependency resolves outside
> that prefix, or if opencc is not the vendored version. Graph B passes it
> automatically; CI's `hermetic-deps` job uses it to build and test against the
> pinned deps, which is the only path that proves the runtime library and the
> committed `.ocd2` files agree. `build-android.sh` additionally checks the
> produced ELF (bionic-only `NEEDED`, exported `rime_get_api`) rather than
> asserting it in prose.

Differences from upstream
===
The engine stays a close derivative, so the list is short and each item is a
dependency question rather than a behaviour change.

  - **No Boost.** `std::regex` plus a minimal `<rime/*.hpp>` shim set replaces the
    boost facilities librime used (algorithm/string, signals2, interprocess, crc,
    uuid, regex, and dll's `shared_library` for plugin loading). Upstream's Boost
    usage is translated at the `#include` line -- the
    shims live in the `boost::` namespace, so call sites are untouched. Constructs
    that cannot be shimmed are replaced at configure time instead (Boost.PP became
    `src/rime_extra_modules.h.in`). The same rule reaches third-party plugins: a
    plugin asking for `<boost/algorithm/string.hpp>` only to call
    `boost::starts_with` is answered from [cmake/plugin-shim](cmake/plugin-shim)
    where the toolchain has no Boost (that header is never installed, and a real
    Boost keeps being used where one exists). Two plugins are out of the plugin
    matrix, for different reasons. librime-charcode's `boost::locale` really does
    carry semantics this fork does not have. librime-lua's exclusion is a scope
    decision, not a Boost impossibility: measured against its current master, its
    Boost use is 3 files / ~70 lines -- `boost::regex` in the regex API functions
    (which `std::regex` plus this fork's PCRE→ECMAScript translation covers, and
    `regex_replace`'s `$1` format already matches ECMAScript), a `boost::optional`
    branch that is dead in a C++17 build because the plugin itself selects
    `std::optional` there, and `boost::signals2::connection` which the plugin does
    not bring in but inherits from librime's own headers, i.e. it names *this*
    fork's replacement signal. The gaps of ours are being closed in order:
    [src/rime/signal.hpp](src/rime/signal.hpp) now has the grouped
    `connect(group, slot)` the plugin's Lua binding calls, ordered the way
    signals2 orders and pinned by `test/signal_test.cc`. What is left is to
    answer `boost/signals2.hpp` (an alias of that same `rime::connection`) and
    `boost/optional.hpp` from the plugin-shim -- in the plugin graph only, because
    an engine header that fakes `namespace boost` would hand a consumer with real
    Boost two different `boost::signals2::connection` types -- and to cross-build
    Lua 5.4, which nobody has done for Android without a Boost tree (Trime still
    builds Boost; fcitx5-android's patches to librime-lua are CMake-level only).
  - **Regex compatibility layer.** Schema-supplied patterns go through a shared
    PCRE→ECMAScript translation ([src/rime/pcre_translator.hpp](src/rime/pcre_translator.hpp)),
    and a bad pattern can no longer take the engine down with it.
  - **OpenCC vendored** ([deps/opencc](deps/opencc)), with the `.ocd2` binaries it
    would otherwise generate at build time committed under `dict/opencc/`, plus a
    mirror of opencc's install directory under `test/opencc/` for `rime_test`
    (`test/CMakeLists.txt` points `Opencc_DICT_DIR` at it on every platform).
    Configure and build need no host Python and no host-built `opencc_dict` -- the
    latter used to break cross-compiling outright (`Exec format error` under NDK).
  - **The shared library builds for more platforms.** commit-ci builds it for
    Linux, macOS, Windows and Android and checks the produced library (Android
    verifies `librime.so` with `readelf -d`); consumers link against it through
    the pure C API ([src/rime_api.h](src/rime_api.h), installed as
    `<prefix>/include/rime_api.h` from `CMakeLists.txt`'s `src/*.h` glob).
  - **A bundled Simplified Chinese dictionary** ([dict/](dict)): `luna_pinyin.dict.yaml`
    + `essay.txt` + the opencc data, published as a versioned artifact
    ([dict/CHANGELOG.md](dict/CHANGELOG.md)). Upstream ships none. Its generators live
    in [dict/tools](dict/tools) and are driven by explicit `make`, never by the CMake
    build graph, so generating data and configuring the engine stay two separate
    jobs. Two gates: `make -C dict/tools check` regenerates and byte-compares the
    committed data, `make -C dict/tools smoke` deploys it and asserts candidate
    behaviour against the real engine. An optional emoji dictionary
    (`dict/opencc/emoji*`, vendored from [rime-emoji](https://github.com/rime/rime-emoji))
    ships with it, switched off by default and toggled with Ctrl+Shift+6.

Syncing upstream
===
```sh
git remote add upstream https://github.com/rime/librime
git fetch upstream
git merge upstream/master        # dict/ has no counterpart upstream; it never conflicts
```

`README.md` is upstream's text with the `Fork.` blocks and the two sections above
added, so a merge only conflicts where upstream rewrote a paragraph around one of
them. Expect conflicts otherwise only where this fork intentionally diverges --
the Boost shims. After merging, `make test` must be green, and
`make -C dict/tools check && make -C dict/tools smoke` must cover the bundled
dictionary.
